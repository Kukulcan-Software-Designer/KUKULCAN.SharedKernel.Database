# Code Coverage

## Scope

The coverage target is the production assembly `KUKULCAN.SharedKernel.Database`.
Test assemblies are excluded from the production coverage measurement.

Coverage is evaluated from two complementary sources:

- **Deterministic unit tests** provide line and branch coverage of the production library.
- **Provider-specific integration tests** validate the same infrastructure against each supported relational DBMS.

The supported providers are:

- Microsoft SQL Server
- PostgreSQL
- MySQL

## Remaining Branch Coverage

The three uncovered branches are all in `KukulcanDbContextBase.ConfigureProvider` at the `switch` over `DatabaseProvider`.

Cobertura reports the switch as:

- **3 of 4 branches covered (75%)** on the switch decision.
- The SQL Server, PostgreSQL and MySQL provider cases are covered.
- The remaining branch corresponds to the `default` case that throws `NotSupportedException` for an unsupported `DatabaseProvider` value.

The relevant production behavior is:

```csharp
switch (_opts.Provider)
{
    case DatabaseProvider.SqlServer:
        ConfigureSqlServer(...);
        break;
    case DatabaseProvider.PostgresSql:
        ConfigurePostgresSql(...);
        break;
    case DatabaseProvider.MySql:
        ConfigureMySql(...);
        break;
    default:
        throw new NotSupportedException(...);
}
```

## Why Coverage Stops at 98.10% Branch Coverage

No further test is added for the remaining `default` branch.

`DatabaseProvider` defines the supported provider contract, and every supported value is already exercised by the test suite. Reaching the final branch requires deliberately supplying a value that is outside that supported contract, for example by casting an arbitrary integer to the enum. Such a test would manufacture an invalid configuration state solely to execute defensive code.

The `default` branch is still valuable production code: it protects the system if an unsupported enum value reaches `ConfigureProvider` in the future. However, its existence does not imply that the current supported behavior needs another test. The branch is a defensive guard rather than an independently supported provider configuration path.

Therefore, increasing branch coverage from **98.10% to 100%** would require a test whose primary purpose is to execute an invalid enum state. That would conflict with the project's behavior-focused testing policy and would not provide proportional additional confidence in the supported persistence behavior.

The decision is consequently to retain the measured **100% line coverage and 98.10% branch coverage** as the intentional coverage baseline for the current implementation.

## Provider Extension Type Resolution

`KukulcanDbContextBase` resolves provider extension types dynamically because the consuming application is responsible for providing the corresponding EF Core provider package.

The resolution logic has three meaningful paths:

1. Resolve the expected fully qualified type directly with `Assembly.GetType(...)`.
2. Fall back to `Assembly.GetTypes()` and match the expected short type name.
3. Handle `ReflectionTypeLoadException` and inspect the loadable types returned by `ReflectionTypeLoadException.Types`.

These provider-resolution paths are covered by the test suite, including the partially loadable provider scenario.

The normal provider configuration path remains unchanged: SQL Server, PostgreSQL and MySQL continue to resolve their provider extension types by the configured assembly and expected type name.

## Connection-String Edge Cases

The connection-string helpers contain explicit defensive handling for empty or whitespace-only connection strings.

The test suite verifies the supported defensive behavior in these helpers, including preserving an empty connection string when there is nothing to process.

## Integration-Test Coverage

Integration coverage must be measured independently for each real DBMS. The provider-specific integration workflows execute against real database engines and should be considered the authoritative source for provider-backed execution coverage.

The aggregate `Coverage.sh` result must not be interpreted as proof that every production line is independently exercised by every database provider. A line executed by one provider is covered in the aggregate report even when another provider does not execute that same path.

| DBMS | Integration coverage |
|---|---:|
| Microsoft SQL Server | **Measured by the SQL Server integration workflow** |
| PostgreSQL | **Measured by the PostgreSQL integration workflow** |
| MySQL | **Measured by the MySQL integration workflow** |

Provider-specific numerical percentages are intentionally kept separate from the aggregate `Coverage.sh` measurement unless the corresponding provider coverage artifact has been explicitly published.

## Test Adequacy Decision

The current test strategy is based on meaningful behavior rather than on manufacturing a coverage percentage.

The combination of deterministic unit tests and real-provider integration tests is the intended coverage model for this project. The latest measurement achieves **100% line coverage** and **98.10% aggregate branch coverage**.

The remaining three branches belong to the defensive unsupported-provider `default` case in `ConfigureProvider`. No additional test is warranted solely to force a 100% branch figure because doing so would require constructing an invalid `DatabaseProvider` value that is outside the supported configuration contract.

## CI Coverage Artifacts

The unit `Code Coverage` workflow generates a Cobertura coverage artifact for the production assembly.

Provider-specific integration workflows generate their own test and coverage artifacts. Those results should be evaluated separately by provider rather than being treated as interchangeable with the aggregate `Coverage.sh` measurement.

## Reproducing the Measurement

From the repository root, run:

```bash
./Coverage.sh
```

The script runs the solution tests, collects Cobertura reports, merges the generated coverage files, and produces the aggregate report used for the figures documented above.

After changes to the coverage suite, the aggregate percentages in this document should only be changed after a fresh `Coverage.sh` execution has produced a new Cobertura report.
